3. MAP PIN FIX - RESOLVED IN THE LIVE CLIENT

Report positions and hover targets existed while pin artwork was invisible.
Changing textures, bundling a TGA and moving to native line artwork did not fix
the map visibility. /cta pincheck showed the same line swords outside the map.
The native MapCanvas DEFAULT layer sits below exploration/fog overlays on this
client. Setting a large numeric level (2000) did not put the pins above them.

Map.lua now uses the managed PIN_FRAME_LEVEL_AREA_POI layer through
MapCanvasPinMixin. Blizzard's frame-level manager places it above exploration
and fog. Pin pooling, normalized positions and mouse handlers stay native.
The regression test asserts relative ordering above those overlays.
Artwork uses six foreground line strokes plus outlines; the old bundled TGA is
not used by the current renderer. No new asset download is needed for this fix.
Pins appear on their matching zone map; continent/world aggregation is not built.
Details and tooltips remain attached to the same report. See MAP_PIN_FIX_0.4.4.txt.

4. CURRENT USER FLOW AND BOUNDS

/cta report, CallToArms.Report(), and binding CALLTOARMS_REPORT invoke the same
one-action report. Binding label: Call to Arms -> Report PvP at my location.
A macro containing /cta report also works through an action-bar binding.
The report anchors to the OBSERVER'S current map and coordinates, not an exact
enemy location or computed battle center. There is no confirmation form.

Normal report: kind=report, unknown fight size. A partial flagged-player sample
does not establish PvP combat. Test mode: /cta test on on BOTH clients, session
only, resets off on reload/login; [TEST] label and purple pin. It includes the
reporter and accessible unflagged players, then fills the simulated count to
four when needed. Synthetic counts never identify fictitious real characters.
Simulation does not change actual PvP/combat flags or emit fake combat events.
/cta demo is local only; /cta test off removes test records and their UI.

Accepted submissions also display locally, using the wire ID to deduplicate
guild self-echo. An accepted send return is not a remote acknowledgement.
No acknowledgements, retransmission, background send queue or delivery guarantee
exist. Failures report a message; the user deliberately retries after debounce.

UI: 300x88 top-right toast for ten seconds; left-click details, right-click
dismiss. Details and activity list retain the report after the toast closes.
Show on map is guarded during combat; the player opens it after combat.
Normal sends: 120-second persisted cooldown. Test sends: separate ten seconds.
Attempt debounce: five seconds. Toast spacing: 30 seconds normal / five test.
Mute suppresses toasts, not storage or map pins. Suppressed toasts are not queued.
Maximum 64 records; five-minute guild-report TTL. Expiry sweep every 15 seconds
while records exist; list reads exclude expired records. Reports are not saved
across reloads. /cta clear clears displays, not report cooldowns.

5. SNAPSHOT SEMANTICS

Report.lua performs one bounded traversal on user input: target, targettarget,
mouseover, focus, up to 40 raid and four party tokens, and 64 nameplate frames.
Normal samples require readable player identity and a true PvP flag. Players
are included only when UnitDistanceSquared returns a usable checked distance
<=10000 square yards. GUID deduplication and a 64-player cap apply.
The player token is explicitly added only in test mode; normal mode must not
automatically count the reporter. Inaccessible/restricted data is skipped where
guarded. complete=false always: this is not a reliable 100-yard census.

unknownRange counts identifiable eligible candidates with unverified distance;
they are NOT additional confirmed nearby players. Out-of-range units are excluded.
Local snapshots contain GUID/name/faction/actual flag/distance and a separate
simulatedCombat field. A.lastSnapshot is transient. Only summary COUNTS are sent
over GUILD; sampled identities never enter this wire format.

No combat-action evidence is currently produced. Flagged bystanders and players
fighting NPCs cannot become verified heat from this snapshot. Before automated
heat, implement and test a permitted evidence source, or agree on a clearly
labeled manual-estimate policy. Duel filtering remains deferred beyond the MVP.

6. CURRENT GUILD WIRE CONTRACT (NOT AN HTTP DTO)

Prefix CTA_REPORT1; route GUILD; one tab-delimited message <=255 bytes.
No chunking, compression, JSON, polling or ordinary-chat parsing.
Exactly 13 fields, in order:
  1 version          literal 1
  2 mode             R (normal) or T (simulated)
  3 nonce            digits-digits-digits, <=40 bytes; server time/uptime/sequence
  4 updatedAt        integer Unix seconds; receive window now-299 to now+30
  5 mapID            integer 1..100000
  6 x                integer 0..10000; round(normalizedX * 10000)
  7 y                integer 0..10000; round(normalizedY * 10000)
  8 faction          H or A
  9 ruleset          normal | pvp | rp | rppvp | hardcore
 10 observedCount    integer 0..64
 11 unknownRange     integer 0..128
 12 syntheticCount   integer 0..4; R requires 0; T requires max(0,4-observed)
 13 region           integer 1..99

Zone text derives locally from mapID. Coordinates are normalized 0..1 after
decoding. Expiry is updatedAt+300. Test count is observed+synthetic; normal count
stays unknown. Titles/notes are reconstructed locally, not free text on the wire.
Reporter comes from the WoW event sender (realm normalized), not a claimed name
in the payload. Record ID: guild:<compact sender hash>:<nonce>. The hash is for
namespacing, not cryptographic authentication or a globally guaranteed identity.

Scope.lua reads actual C_GameRules flags (HardcoreRuleset/RPRuleset/PvPRuleset)
and GetCurrentRegion. Unknown/error/secret values disable network reporting.
Hardcore takes precedence. No user ruleset override can redirect network reports.
Receive requires matching region, ruleset and faction. Scope changes clear local
records. No realm or layer field exists; do not infer a layer from sender realm.

GUILD limits reach to guild members, not every addon user or another guild.
Underlying broadcast bytes can reach other guild members before our client
filters them. Audience filtering is not confidentiality or verification of a
sender's claimed faction/ruleset. There is no community/organizer authorization.

Receive rejects wrong prefix/route/scope, invalid fields/times, secret values,
duplicates and test packets without opt-in. Per-sender limits are 120 seconds
normal / ten test; global budget is 12 messages with refill of one per second;
rate bookkeeping is bounded to 128 entries. There is no area-based deduplication
between different observers. Keep that gap separate from same-ID deduplication.

7. LUA EXTENSION BOUNDARY

After initialization, CallToArms.Version=1 is the API contract version (not the
release number). CallToArms.Report() invokes reporting; Receive(record) validates
and displays a Lua table. SetTransport(callback) replaces the default guild
adapter. The synchronous callback receives the local request and returns
true, message only when accepted for dispatch, or false, reason. Calls are
protected with pcall; no yielding or unbounded queues. SetTransport(nil) detaches
it and leaves local-preview behavior. No HTTP bridge is implied by this hook.

Local outbound requests include manual=true, kind=report, map/coordinates,
audience, timestamps, a temporary local:<time> ID, snapshot and summary counts.
GuildTransport replaces the temporary ID with the sender/nonce wire identity.
Do not use the temporary local ID as a globally unique backend idempotency key.

Receive display model (Model.lua; plain non-secret values only):
  version=1; id nonempty <=80 bytes (%w, underscore, colon, hyphen, dot)
  kind=report|defense|raid|heat; faction/ruleset must match local display scope
  mapID integer 1..100000; x/y finite 0..1; count integer 0..1000
  updatedAt now-3600..now+30; expiresAt now+1..now+3600 and >updatedAt
  heat additionally requires count>=4, countUnknown false and cityAllowed=true
  title<=72, reporter/opposition<=64, note<=160 bytes; markup/control text cleaned
  estimated/demo/test booleans; optional observed/unknown/synthetic summary counts

Normal report count is always unknown. Same ID requires a strictly newer update;
same-ID updates do not produce another toast. Model limits differ from the more
restrictive guild decoder. Region is checked in the guild adapter, not in this
generic display model. Adapter validation/authorization must precede Receive.
cityAllowed is only a display gate; no implemented city/organizer authority
backs it. Guild packets support report only, never heat/raid/defense creation.
Detailed snapshots are not retained by Model.lua. Text limits are byte-based.
No tombstones, cancellation protocol, layer schema or delivery receipts exist.

8. AGREED PRODUCT REQUIREMENTS STILL TO BUILD

* Heat requires four DISTINCT actual local PvP participants in any combination,
  including 3v1; pets do not add players. Reports originate with local observers
  or addon-equipped participants. No worldwide scanning or assumed coverage.
* Any addon user may issue a defensive observer report. Current transport still
  requires guild membership; unaffiliated/cross-guild reach is not implemented.
* Registered guilds/communities can create CTAs within the appropriate ruleset
  and faction. Organizer roles must be verified. Opposing guild/group attribution
  is optional reported information, not authoritative identification.
* Ordinary automatic city heat is suppressed. Authorized city-raid CTAs go to
  the attacking faction; a scheduled invitation alone must not produce heat.
  Once active, minimal city status (city/event/window) may enable an exception.
  Defenders still need their own faction's fresh observer/participant evidence.
  Do not expose attacking invitation/rally/private organizer data to defenders.
  End/expire the exception when the raid ends or evidence becomes stale.
* Keep Blizzard's native map and bounded event-driven Lua. No terrain engine,
  per-frame scan or mandatory third-party library. Heavy aggregation belongs
  outside the lightweight renderer, once a usable transport is established.

Proposed future service responsibilities (not implemented): authenticated
community membership; ingress validation and reporter+nonce idempotency;
encounter aggregation with evidence class and distinct participants; city-event
lifecycle; audience fan-out; bounded queues, expiry and abuse controls; short,
explicit retention and delivery/rejection observability. Database/hosting and
retention duration are undecided. See BACKEND_STACK.txt for the C# recommendation.

Do not sum overlapping snapshots or count observers as fighters. Clustering
requires map-aware physical distances; normalized map deltas are not yards.
The requested 100-yard sample is not an agreed encounter-clustering radius.
Do not merge known distinct layers. Reuse encounter IDs to avoid duplicate
toasts; severity-escalation notification policy remains undecided.
City state proposal: scheduled -> active -> ended/cancelled/expired, with
activation authority, timeouts and map/subzone boundary data still to define.
